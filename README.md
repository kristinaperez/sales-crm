# CRM холодных продаж

Веб-CRM для отдела холодных B2B-продаж: до 10 менеджеров и руководитель, до 10 000 компаний.
Главный сценарий — загрузить список компаний, проверить распознанные строки, убрать дубли,
назначить ответственных и вести сделки от первого обращения до оплаты.

Стек: FastAPI, SQLAlchemy, Alembic, Jinja2, SQLite (WAL). Интерфейс на русском, запуск через Docker Compose.

## Запуск

```bash
cp .env.example .env        # при желании задайте ADMIN_PASSWORD и порт
docker compose up -d --build
```

Приложение: <http://localhost:8000>

Первый вход — руководитель, логин `head`. Пароль берётся из `ADMIN_PASSWORD`; если он не задан,
пароль генерируется и один раз печатается в логах:

```bash
docker compose logs crm | grep -A3 "Создан руководитель"
```

Менеджеров руководитель добавляет в «Настройки → Сотрудники».

### С демоданными

```bash
SEED_DEMO=1 ADMIN_PASSWORD=придумайте-пароль docker compose up -d --build
```

На пустой базе появятся восемь компаний со сделками на разных этапах и два менеджера:
`anna` и `boris`, пароль `demo-crm-2026`. Для боевой базы демоданные не включайте
(или сразу смените пароли и отключите демо-менеджеров).

## Что умеет

**Импорт (руководитель).** Четыре входа: вставка текста / списка ссылок / ответа ИИ с Markdown-таблицей,
TXT-файл, CSV с сопоставлением колонок, диапазон из Google Таблиц. Перед записью — предпросмотр
со статусами «Новая компания», «Возможный дубль», «Нужно проверить»; строки можно поправить,
исключить, а для подсказки «похожи название и город» — всё равно создать. После подтверждения
показывается, сколько строк создано, отправлено на проверку, пропущено и исключено.

- Дубли ищутся по нормализованному адресу официального сайта (без `https://`, `www.`, пути, регистра;
  кириллические домены сравниваются в punycode). Совпадение названия и города — только подсказка.
- Ссылки на соцсети, карты, каталоги и мессенджеры сохраняются как ссылки и сайтом компании не считаются
  (список доменов — `app/services/normalize.py`).
- Если есть только ссылка, карточка создаётся со статусом «Нужно проверить».
- У каждой карточки хранится источник и исходная строка списка.
- Повторная загрузка того же списка новых карточек не создаёт; ручные правки, ответственные,
  этапы и история остаются как были. Строки, исключённые в прошлый раз, сами не возвращаются.
- Ссылки — это данные: CRM не открывает сайты и не вызывает внешние ИИ-сервисы.
- Подтверждение идёт короткими транзакциями по 250 строк; каждая заново ищет совпадения
  перед записью, поэтому параллельные импорты не создают дубль. Прерванный импорт можно продолжить.

**Компании, контакты, сделки.** Компания: название, сайт, город, отрасль, телефон, email, мессенджер,
источник, заметка, ссылки, контактные лица. Сделка привязана к компании: воронка, этап, ответственный,
следующий шаг со сроком, причина отказа. У компании может быть несколько сделок.

**Воронка.** Готовая: Новая → Готова к контакту → Первый контакт → Есть ответ → Демо → Предложение →
Оплачено / Закрыто без продажи. Руководитель добавляет воронки и настраивает этапы
(«Настройки → Воронки»), там же задаётся, какой этап считается в отчёте первым контактом, ответом, демо и оплатой.

**Работа менеджера.** В карточке сделки одна форма «Что сделано»: тип (сообщение, звонок, письмо, заметка),
результат, новый этап и дата повторного контакта — повторный контакт становится задачей со сроком.
Экран «Мои задачи»: «Сегодня», «Просрочено», «Без следующего шага» (только открытые сделки).

**Руководитель.** Общая база, фильтры по городу, отрасли, этапу и менеджеру, массовое назначение
(несколько менеджеров — сделки делятся поровну), экспорт CSV, отчёт по менеджерам за период.

**Права.** Менеджер видит только сделки, где он ответственный, и карточки этих компаний.
Проверка — на сервере для каждого запроса; чужая сделка по прямой ссылке отдаёт 404.

**Одновременная работа.** У сделки есть номер версии. Если двое одновременно меняют этап или
ответственного, второй получает сообщение о конфликте и видит актуальное состояние.

## Резервная копия и восстановление

База, ключ сессий и копии лежат на томе `crm-data` (в контейнере — `/data`), том переживает
пересоздание контейнера. **Экспорт CSV — для работы с таблицами; он не заменяет резервную копию.**
В копию попадает вся база: компании, контакты, сделки, задачи, история, пользователи, импорты.

Сделать копию (приложение можно не останавливать):

```bash
docker compose exec crm python -m app.cli backup            # файл /data/backups/crm-ГГГГММДД-ЧЧММСС.db
docker compose cp crm:/data/backups ./backups               # забрать копии с тома на сервер
```

Храните копии не только на этом сервере. Пример ежедневной копии в cron сервера:

```cron
30 3 * * * cd /opt/sales-crm && docker compose exec -T crm python -m app.cli backup && docker compose cp crm:/data/backups ./backups
```

Восстановить:

```bash
docker compose stop crm
docker compose cp ./backups/crm-20261116-033000.db crm:/data/restore.db
docker compose run --rm --entrypoint python crm -m app.cli restore /data/restore.db
docker compose start crm
```

Перед заменой текущая база сохраняется рядом как `crm.db.before-restore-…`.
Раз в месяц проверяйте восстановление на копии — резервная копия полезна, только если из неё удаётся подняться.

## Настройки (.env)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CRM_PORT` | `8000` | Порт на сервере |
| `DATABASE_URL` | `sqlite:////data/crm.db` | Подключение к базе |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `ADMIN_NAME` | `head`, —, «Руководитель» | Руководитель при первом запуске |
| `APP_TZ` | `Europe/Moscow` | Часовой пояс для «Сегодня» и «Просрочено» |
| `SEED_DEMO` | `0` | `1` — демоданные на пустой базе |
| `SECRET_KEY` | создаётся на томе | Ключ подписи сессий |
| `SESSION_HTTPS_ONLY` | `0` | `1`, когда CRM открыта по HTTPS |
| `FORWARDED_ALLOW_IPS` | `127.0.0.1` | Адрес обратного прокси, которому можно доверять |

**Доступ из интернета.** Ставьте CRM за обратным прокси с HTTPS (Caddy, nginx, Traefik) и включайте
`SESSION_HTTPS_ONLY=1`. Прокси должен передавать исходный заголовок `Host`
(в nginx: `proxy_set_header Host $host;`) — по нему CRM отличает свои формы от чужих запросов.

## Разработка

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
alembic upgrade head && python -m app.cli init && python -m app.cli seed-demo
uvicorn app.main:app --reload
pytest
```

Локально база лежит в `./data/crm.db`. Служебные команды: `python -m app.cli` (init, seed-demo,
create-user, set-password, backup, restore).

Структура:

```
app/models.py            модель данных
app/services/            бизнес-логика без HTTP: импорт, сделки, права, списки, отчёт
app/web/                 обработчики страниц (тонкие: разбор формы → сервис → шаблон)
app/templates, static    интерфейс
alembic/                 миграции схемы
tests/                   модульные тесты и сквозной сценарий
```

Изменение схемы: поправить `app/models.py`, затем
`alembic revision --autogenerate -m "что изменилось"` и `alembic upgrade head`
(в контейнере миграции применяются при каждом старте).

## Переход на PostgreSQL

Схема ведётся миграциями, подключение задаётся `DATABASE_URL`, бизнес-логика не использует
особенностей SQLite, кроме настроек подключения в `app/db.py`. Порядок перехода:

1. Добавить драйвер (`psycopg[binary]`) в `requirements.txt`, поднять PostgreSQL.
2. `DATABASE_URL=postgresql+psycopg://user:pass@host/crm alembic upgrade head` — создаст ту же схему.
3. Перенести данные из файла SQLite (например, `pgloader` в режиме «только данные») и выставить
   значения последовательностей id.
4. Запустить приложение с новым `DATABASE_URL` и прогнать `pytest` на копии.

В этой версии приложение проверено только на SQLite; на PostgreSQL тесты ещё не запускались.

## Что не входит в первую версию

- Обход сайтов и обогащение карточек, вызовы внешнего ИИ.
- Отправка сообщений и звонки из CRM: менеджеры пишут и звонят вручную, в CRM фиксируют результат.
- Перетаскивание карточек в воронке (этап меняется выбором из списка).
- Объединение уже созданных дублей в одну карточку.
